# Production migration, deployment and recovery runbook — NOT execution authorization

This runbook is prepared locally. **Do not run production commands until each access/action is separately approved.** The startup prohibition remains unchanged and rejects every persistent/customer database. No approved production ownership manifest, inventory, backup or restoration evidence is available. Deployment is BLOCKED.

## 1. Establish the candidate and private evidence

Name accountable release operator, data owner, security approver and recovery decision maker. Record the exact Git commit, source-tree fingerprint, dependency lockfiles, built backend/frontend hashes, Java/Node/PostgreSQL versions, checksums for every migration, CI run IDs and all local results. Current foundation migrations are V1,V2,V4,V5,V6; **there is no operational V3**. Do not skip this blocker because an empty synthetic database can reach V6.

Build and run `./scripts/verify-release.sh` locally with Docker, Java17 and Node22, installed locked frontend dependencies, Playwright CLI0.1.22 and its Chrome dependency. It creates only owned, marked disposable databases; it accepts no database connection or deployment arguments. `./gym-backend/scripts/rehearse-tenant-migration.sh` separately reruns synthetic mapping/restore cases. Candidate verification does not imply permission to publish/deploy. Re-run on the exact final approved release commit and archive a sanitized evidence manifest privately. A local uncommitted tree is not a remotely certified release artifact.

## 2. Inventory before any migration or baseline

Obtain separate authorization for read-only production metadata and any customer-account review. Use a verified read-only role, explicitly approved endpoint/database/schema and no inherited psql startup file. Only then execute the prepared `docs/sql/phase6-schema-inventory.sql`, with `review_schema` supplied explicitly. Output stays private outside Git/CI/screenshots. Verify actual PostgreSQL major/patch, schema, Flyway history/checksums if present, columns/types/nullability/defaults, unique/FK/check constraints, indexes/partitions, triggers/functions, extensions, owners/ACLs, sequences, time zone, database size and lock/transaction activity. Inspect unknown schemas/triggers/functions, not just ORM entities. Never point the disposable harness at this database.

Certify the actual legacy schema against the source-derived V1 and its fingerprint before an explicit baseline. V1 must not recreate populated customer tables. V2 refuses an unknown baseline; do not edit its checksum or use Flyway repair to disguise drift. Review actual applied Hibernate changes; transition away from update only after inventory reconciliation. No automatic baseline, clean, schema update or application-driven migration is permitted.

## 3. Ownership and conflict approvals

Every legacy account needs an explicit account-ID-to-gym decision, including disabled accounts and administrators. No account is assigned by email domain, relationships, account role or a universal legacy gym assumption. A legacy gym is created only if named/approved in the manifest. Accounts with unresolved ownership remain untouched; the cutover is blocked until all required assignments are resolved.

The private manifest contract must include: format/revision, target database/schema identity, reviewed source commit/migration checksums, consistent snapshot identifier and full source counts/digests, approval references and independently verified sign-off, gyms with UUID/name/slug/status, enabled primary-owner selections, explicit user assignments, original catalog ownership, catalog clone and old/new reference maps, approved owner-role changes, historical cross-gym booking resolution and expected after-state differences. Bind the manifest checksum to the exact inventory. Reject missing/duplicate/unknown IDs, partial mappings, disabled owner selection, stale snapshots, conflicting relationships and changed counts. Keep mapping inputs/receipts in an operator-only schema/storage unavailable to runtime. An approval string in software is not proof of human authorization. No real manifest is supplied in this repository.

Membership overlaps are not migration choices. Use the existing private read-only audit/review workflow under separate data approval; preserve historical periods and book dates/statuses/values. Do not cancel/merge an overlapping period or select a winner automatically. Resolve disputed behavior separately, with pre/post reconciliation and rollback receipt. Preserve disabled-admin status, passwords/UUIDs/creation times and business relationships; only explicitly approved owners are promoted. Platform administration remains separate from gym ADMIN.

For shared catalogs, approve which gym keeps each original ID. Assign original catalog ownership, establish gym-scoped uniqueness, and remove obsolete global uniqueness in the same V3 transaction **before** inserting identical clones and their collections. Remap only explicitly approved membership plan/exercise references. Preserve original membership/log/session IDs, dates/statuses/value fields; record approved FK differences. Advance sequences after explicit inserted/copied IDs. Reject a historical booking whose member/trainer map to different gyms; do not rewrite it silently.

## 4. Backup and verified recovery gate

Choose and approve RPO/RTO and archive retention; none is certified. Verify PostgreSQL-compatible dump/restore tooling and roles; `pg_dump` does not include cluster-global roles/tablespaces. Capture these separately with restricted handling, excluding unnecessary role password material. For a cutover, freeze writes, drain requests/jobs/old instances and verify no writers remain. Take a consistent pre-cutover custom archive plus schema/roles/ACL/sequence inventory, compute SHA256, encrypt it and store in approved durable storage with independently tested access. Do not treat an untested dump file as a verified backup.

Restore the exact archive into a new, access-isolated target; enforce no application/provider egress. Use exit-on-error and single-transaction where supported, verify restore exit status, archive hash and complete private reconciliation. **Using no-owner/no-privileges requires explicit recreation of all reviewed ownership/ACLs and REVOKEs.** The synthetic rehearsal proved no-privileges restores a default PUBLIC EXECUTE grant on the restricted catalog helper unless its REVOKE is reapplied. Revoke helper EXECUTE from PUBLIC and runtime, recreate only approved runtime grants, and verify no schema/table ownership or owner-role membership leaks to the app.

Reconcile every table and sequence, IDs/credentials/role/enabled state, per-gym counts, membership/history values and overlaps, trainer/member links, collection values, approved catalog clones/FK remaps, constraints/triggers and Flyway history. Exercise the exact tenant-aware candidate using non-DDL runtime credentials, both gyms and negative foreign-ID operations. Measure archive/restore/reconciliation durations, database size and candidate smoke tests. Independently approve evidence before any production cutover. Local synthetic restoration proves the procedure only; it does not prove the real backup is complete, accessible or timely.

## 5. Migration order and failure handling

After write freeze, backup sign-off, manifest approval and certified inventory:

1. Adopt a verified existing schema through an explicit V1 baseline only when required; otherwise V1 initializes a clean target. Record the exact action/history.
2. V2 expands nullable ownership and domain support. It must match the certified V1 schema.
3. **Implement/review the separately controlled operational V3 first.** Validate full manifest/snapshot and execute gym/user/catalog assignments, scoped uniqueness before clones, remaps, dependent ownership and approved owner changes atomically with bounded lock/statement timeouts and deterministic ordering. Assert completeness, same-gym links and enabled primary owners before committing. No fallback/default gym. Private checksum-bound receipts required.
4. V4 enforces non-null ownership, composite gym FKs, immutable gym/primary-owner rules, deferred owner invariant and indexes.
5. V5 installs authorization-version enforcement; V6 permits MEMBER/TRAINER invitations only. Verify checksums, constraints/functions/triggers and sequences, then remove runtime access to operator inputs and DDL helpers.
6. Independently reconcile all expected differences and approved unchanged historical fields before allowing traffic. Leave Hibernate validate, SQL-init never and app Flyway off; demo/onboarding and S3 remain off.

Each successful version is a separate committed transaction. A later failure does not undo earlier versions. On failure after V2, keep writers stopped and inspect history before resuming from the approved mapping stage. On V3 failure, its transaction must revert assignments/clones/constraint transition; verify that rollback, not just an exception. On V4 or later failure, V3 mapping may already be committed; remain offline, inspect actual applied history/schema and either apply a reviewed forward fix or restore the approved pre-cutover backup. Do not run Flyway clean, auto-baseline, repair or automatic down migrations. Never restart an old unscoped app to work around enforcement errors.

Synthetic evidence includes backups/restores at V2,V4,V5,V6; explicit mapping preserves overlaps/disabled admin; cross-gym historical booking blocks V4; failed clone/mapping rolls back global uniqueness transition. Operational V3 execution/failure injection and real lock/index timing remain BLOCKED until that runner and the target inventory are approved.

## 6. Runtime privilege and configuration contract

Separate migration ownership from the runtime login. Runtime must be NOSUPERUSER/NOCREATEDB/NOCREATEROLE/NOBYPASSRLS, own no schema/business tables and have no membership in their owner roles; deny schema CREATE, TRUNCATE and DDL. Grant required schema USAGE and SELECT/INSERT/UPDATE/DELETE on the 23 approved business tables, USAGE/SELECT on required sequences and **SELECT only** on Flyway history. Do not grant history mutation, operator-input access, or catalog-scoping helper EXECUTE. Verify trigger/function execution and real owner/invitation/membership operations through runtime credentials. DB grants are defense in depth; shared-database table grants do not themselves enforce tenant row isolation. Backend predicates and reference validation remain required.

Use approved secret management for per-environment DB credentials and a strong private JWT signing key; reject known demo keys, avoid inherited connection overrides, scope CORS to exact HTTPS frontend origins (loopback origins only for local tests), preserve credentialless bearer CORS and do not enable forwarded headers without a reviewed proxy/hop allowlist. Set migration/SQL-init off, ddl-auto validate, S3/demo/email provider disabled. Readiness also rejects unsafe/missing runtime privileges, incompatible history and schema-contract drift; it returns minimal READY/NOT_READY and never customer/schema details. It is a technical probe, not approval of V3, backups, provider readiness or release.

Review browser bearer storage, TLS, frontend security headers, distributed limiter/proxy topology, verified-email/recovery design, secret rotation, request/SQL logging privacy and monitoring retention before release. Unexpected application exceptions now log type rather than payload/stack; framework/driver warnings can still contain row values and require a production redaction/log-level/retention decision. Do not enable Hibernate parameter logs. Preserve the startup prohibition until a separate reviewed rollout replaces it; changing a flag is not a permitted bypass.

## 7. Coordinated deployment and smoke tests — only after authorization

Obtain specific authorization for infrastructure changes, production SQL, startup-guard replacement and the exact compatible frontend/backend release. Do not enable automatic production deploys. Keep a maintenance boundary through migration/reconciliation; stop every old writer before switching either application artifact. Expire all legacy JWT schemas by the existing schema2 requirement; coordinate signing-key/credential/authz-version rotation and fresh login as approved. Deploy matched artifacts together; route version compatibility must include owner/invitation/auth-me behavior and V6 schema. Do not assume a cached old frontend is compatible; approve cache/version-refresh policy.

With runtime credentials, check liveness and readiness, owner/member/trainer/admin login/session restoration, local lists and aggregates, both directions of foreign-ID rejection including nested writes, owner protection, member/trainer profiles, membership purchase/renew/upgrade and conflict behavior, booking/overlap/adjacency, attendance, workouts/nutrition/progress, dashboards, notifications and CSV gym separation. Onboarding/email remain disabled until their own implementation/approval. Verify no S3 writes or external mail. These are proposed production smoke tests, not actions run in this phase.

## 8. Monitoring and recovery decisions

Use bounded tenant-ID labels derived from authenticated accounts, status/error category and request correlation IDs; no passwords, email bodies, JWTs or invitation links. Alert on readiness failures, 5xx, unusual401/403/404/429 rates, DB pool/locks/deadlocks, migration failures, owner invariant violations, backup age/restore drift, verification/limiter/provider failures after activation, and gym-specific isolation anomalies. Audit OWNER/ADMIN actions with authenticated actor/target/gym, protected retention and access. Existing logs carry trusted gym/user/role but no durable production audit/alert system is configured; this remains an operational gate.

Before traffic: any mismatch, failed negative test, invalid owner, missing ACL, backup/manifest uncertainty or incompatible schema keeps maintenance active. Decide forward fix versus restoring the exact pre-cutover backup while no newer writes exist. After traffic: prefer a forward fix or approved older **tenant-aware, schema-compatible** artifacts; never roll back to 4ad9632 or any unscoped version against multiple gyms. If restoring an old database after new writes, quantify and approve lost/replayed data and tenant-specific reconciliation; RPO/RTO must drive the decision. A rollback is a new explicitly authorized operation. Preserve failed-state evidence privately and verify recovery before reopening traffic.
