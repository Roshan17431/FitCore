# Phase 9C — gym catalog management design for approval

4 November2026. Source e669f08, isolated codex/phase9a-clean-instance. Only disposable PostgreSQL/synthetic fixtures/local UI. No commits, push, deployment, real mail, persistent DB, global seeds or startup-guard change.

## Approaches

Recommended: retain existing string-based workout-plan exercise collections, validate new selections through same-gym exercise IDs and preserve names once referenced. Add minimal archival/publication fields and manager APIs/UI. This preserves existing history and avoids inferring migrations for legacy name lists. Alternative: introduce normalized plan/exercise links and versioned history snapshots; supports broader renaming but requires a larger data-compatibility design and migration. The alternative is outside the proposed implementation.

## Proposed domain behavior

V9 only: add exercises.archived boolean NOT NULL default false, nutrition_plans.archived boolean NOT NULL default false, workout_plans.status varchar NOT NULL default PUBLISHED with DRAFT/PUBLISHED/ARCHIVED check. Existing catalogs stay visible without seeding/reassigning gyms; new managed workout plans start DRAFT unless explicitly validly published. Existing V1–V8 untouched. Fresh/current/restore schema/history certification moves to V9 with independently compared exact fingerprints. Extend the descriptor to include normalized column defaults and add default-drift negatives, strengthening certification of the new defaults while retaining all negative security checks; V8-only database must not report ready for V9 application.

Exercise managers can create/update description/category/difficulty/sets/reps/image. Reject renaming if any same-gym workout history or plan references its existing name; instruct manager to create a replacement instead. No deletes. Archival hides an exercise from new-use lists but preserves history reads. Reject archival while a published workout plan contains it; require manager to edit/archive that plan first. Drafts may retain archived references but cannot publish them. New workout logging rejects archived exercises; historical log values/IDs and labels remain intact.

Workout managers can create/edit level, duration, supported bounded duration/schedule text (no invented duration/schedule enums) and string list and local exercise selections; publish or archive. New exercise selections carry exercise IDs only, each checked in actor gym; persist canonical names in the existing collection. On update an omitted exerciseIds field preserves existing names; an explicit empty list clears selections and is valid only for a draft. The UI omits unchanged selections and visibly lists unresolved legacy names, never drops them on form load/save. Metadata-only legacy edits may retain their unchanged publication/list state; new publication or changed selections while published must resolve every exercise locally and actively. Empty drafts allowed, publication requires at least one active local exercise and no unresolved legacy exercise name. Existing legacy name lists remain unchanged unless the manager explicitly replaces them with valid local selections. No automatic mapping, deletion or bulk rename. Existing log schema has no workout-plan foreign key; plan edits never rewrite activity.

Nutrition managers can create/edit category, calories/protein/carbs/fats and bounded plain-text meal strings (maximum255 characters per existing collection column; current list ordering is unspecified); archive without deleting. Meals are owned collection strings, not standalone entities, so clients cannot supply meal/gym ownership IDs. Label all nutrition figures as gym-provided estimates and replace existing catalog “daily target” wording. No medical claims or dietary prescribing functionality.

Keep existing case-sensitive gym-scoped uniqueness on exercise name, workout level and nutrition category, including archived records; no name recycling. Trim input, enforce nonblank/bounded strings/lists, nonnegative bounded macro values, valid enum/duration fields and distinct valid exercise IDs. Render plain text. Image changes accept safe project-local image paths or HTTPS origins from an explicitly configured allowlist (default no external hosts); library image rendering must use reviewed references with the current fallback and must not start loading arbitrary legacy external URLs; no fetch/upload/new S3 activation. Existing unchanged legacy image references may be retained without legitimizing new arbitrary references.

## Tenant and transaction controls

New /api/admin/catalog endpoints restricted to OWNER/ADMIN both HTTP and service boundary. Every list/item/write resolves gym from TenantActor and tenant-qualified repository lookups; DTOs expose no writable gym/owner fields. Foreign item/nested exercise IDs fail404; invalid payload400; duplicate/reference conflicts409. MEMBER/TRAINER writes403. No platform/global ADMIN bypass.

Serialize manager changes through the gym row and lock affected exercise rows consistently by ID. Workout logging obtains its initial exercise lookups with read locks in ascending ID order and reuses these entities through insertion (no prior unlocked entity cache); manager rename/archive takes the conflicting write lock before reference checks. Keep default PostgreSQL/Hibernate FK-compatible NO KEY UPDATE gym lock behavior; no NOWAIT/SKIP LOCKED variant. This prevents rename/archive-versus-log races. Multi-record mutations are transactional; validate every nested reference before committing collections. No membership/booking concurrency/business changes.

Regular read endpoints retain existing DTO formats and show active exercises, PUBLISHED workouts and unarchived nutrition plans; manager endpoints include draft/archive state. History still resolves archived exercises. Owners can see all manager records. No automatic shared catalogs.

## Frontend

Reuse emerald/graphite components, forms/modal/notifications and existing OWNER/ADMIN route guard. Add /gym/catalogs with exercise, workout and nutrition sections; searchable exercise/category filters, create/edit forms, local-exercise selectors, schedule/meal editors, publish/archive controls and archive confirmation. Support desktop/mobile/light/dark and accessible labels/error/focus states. New empty states on membership/workout/exercise/nutrition libraries offer OWNER/ADMIN links to existing membership management or new catalog screens. MEMBER/TRAINER see informative copy only. Do not redesign dashboards or change browser token transport.
