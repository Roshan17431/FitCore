# Production onboarding security — original Phase 6 design

Historical design retained. Verification, reset and shared abuse controls are now implemented locally in [the security-closure report](security-blocker-closure-2026-11-01.md). The descriptions below record the pre-implementation state; external delivery and production activation remain blocked.

Current code deliberately has no email ownership verification, real invitation delivery, or password-reset completion. Owner/invitation signup remains disabled by default and restricted to an owned local demo. Password-reset requests return generic202; the UI truthfully directs users to an administrator. A new `TransactionalEmailSender` boundary is configurable through `fitcore.email.provider`, but **only disabled is implemented**. Its send method always refuses; selecting an unknown/real provider fails bean initialization. No credentials, SDK, send attempt, outbox worker or new public auth endpoint is introduced.

## Required production flows

**Owner creation:** use a pending registration outside `users` and `gyms`, verify email ownership first, then atomically create the enabled OWNER, gym and primary-owner relationship using the existing transaction. Creating a disabled primary OWNER pending verification would conflict with the database's enabled-primary-owner invariant. Do not weaken that invariant. Hash the password with the approved policy; pending records expire and are cleaned without creating gym/account orphans. Recheck global email and gym slug uniqueness at completion under database constraints. Never assert that existing accounts have verified ownership without separate evidence.

**Invited member/trainer:** issuer remains the current authenticated OWNER/ADMIN of an active gym. Role and gym come only from the stored invitation. Verification must bind the exact invited email and stored invitation ID; a browser-supplied role/gym cannot override either. Verify email before the existing final atomic user/profile/invitation-consumption transaction. Recheck invitation expiry/revocation, gym status, address binding and uniqueness at completion. Generic public responses cover unavailable/reused/unknown inputs. Changing the invited address requires a new invitation, not an update from the recipient.

**Password reset:** generic202 for existing, disabled and nonexistent addresses with no recipient/account detail. Use a challenge bound to stable user ID, normalized email, credential/authorization version, purpose and expiry. Final POST atomically locks/consumes the challenge and updates the password. Existing V5 and credential-version logic invalidate old JWTs. Revoke outstanding reset challenges and require fresh login. Do not allow public recovery to change gym/roles/enabled state or reactivate a suspended gym. Owner recovery requires an approved identity/recovery process that preserves the primary-owner invariant; ordinary ADMIN cannot recover/promote an OWNER by changing role.

## Token and delivery contract

- Generate at least256 random bits with a CSPRNG; store only a cryptographic digest in challenge rows. Explicit purposes: verify-owner, verify-invite, reset-password. No token can cross purposes/accounts/emails/invitations. Unique digest, expiry and consumed/revoked timestamps; index expiry for bounded cleanup. Proposed TTL: verification24h, reset15min; invitation48h remains the existing rule. These are proposed production policy values, not enabled settings.
- Single-use conditional consumption under transaction/row lock; concurrent redemption yields one success. Resend rotates/revokes prior verification challenges. Requesting a password reset must not invalidate a signed-in user before successful completion.
- Links use an approved fixed frontend origin, fragment capture and POST body; never derive a link origin from an arbitrary Host/forwarding header. Remove fragments immediately on initial and same-document navigation; do not mutate state with GET or allow redirect parameters to choose external origins.
- Never log token/password/body/recipient/provider payload or persist plaintext secrets in analytics/browser storage. A durable delivery/outbox design needs an approved encrypted payload/KMS scheme for retries; hashed challenges alone cannot reconstruct a token. Provider envelope secrets, private keys, sender domain/DKIM/SPF/DMARC, bounce handling, retention and worker access require separate provisioning/approval.
- Provider implementation must have bounded timeouts, recipient/header validation, fixed templates, idempotency, safe retry/dead-letter handling and a sandbox transport for tests. Real sending remains disabled until provider/domain/credentials and data handling are approved. Current disabled bean does not claim those capabilities.

## Distributed abuse controls and enumeration

Current onboarding limiter is a bounded single-process window and is not production distributed protection. Implement atomic distributed counters (approved shared store) for global, trusted remote address, email digest, invitation/challenge digest and issuer-account/gym limits; separately cover login, reset and resend. Public endpoints must fail closed or use a documented restricted fallback when the limiter is unavailable. Do not use unverified X-Forwarded-For to key limits. Set trusted proxy/hop configuration only after topology review; current code uses the direct servlet peer address. Avoid locking a victim's account merely because someone submits their email. Generic messages alone do not guarantee timing equivalence; test mail/no-mail outcomes and response timing under load.

## Acceptance gate before enabling public onboarding

BLOCKED until implemented and tested: account/verification state migration, pending-owner design, email/reset token issuance and expiration, purpose/binding/replay/concurrency tests, existing-email behavior without leaks, transactional outbox and provider retries, distributed rate limits/failure behavior, trusted proxy topology, malicious redirect/header cases, generic public errors, reset-driven session revocation, owner recovery, accessible frontend completion screens, privacy-safe logs, and explicit activation approval. Test only with synthetic recipients and fake/sandbox transport; real delivery needs separate authorization.

Browser bearer tokens remain in local/session storage for compatibility; an XSS can steal them. A production HttpOnly Secure SameSite cookie/BFF/CSRF design or an explicitly accepted mitigation decision is required before release. Do not silently introduce cookies while keeping current CSRF-disabled stateless security. Exact CORS and removing credentialed CORS are appropriate for the existing bearer transport, not a substitute for CSRF controls after a cookie transition.

Primary guidance: [OWASP forgot-password guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) and [authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html). These are requirements for the future implementation, not evidence that it exists today.
