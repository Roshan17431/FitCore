# Certified startup contract for the independent FitCore SaaS

**Proposed for review. Persistent startup remains blocked.** This contract covers Option A, a separate FitCore instance with an initially empty PostgreSQL database. The existing [release checklist](multi-tenant-release-checklist.md) governs launch. The contract and test fixture introduce no runtime startup path.

## Current protections

- [FoundationSafetyConfiguration](../gym-backend/src/main/java/com/fitcore/gym/config/FoundationSafetyConfiguration.java) installs a static Spring bean factory post-processor. It rejects S3 activation and forwarding modes other than `none`. Before datasource initialization, Boot’s relaxed binding checks for Hikari URL, datasource class, JNDI, instance, driver and datasource properties, Spring datasource type or JNDI, and Flyway URL, driver and JDBC properties. The `FoundationSafetyTest` suite exercises these connection selectors, including environment aliases.
- The guard accepts a narrow in-memory H2 URL for tests. PostgreSQL requires a query-free loopback URL with the fixture database name `fitcore_phase2` or `fitcore_phase2_e2e`, a 64-character lowercase hexadecimal test token, and a live database comment matching that token. A nonmatching URL or token fails before the guard dials. A failed connection or marker check stops startup. The marker proves only the current fixture convention. The guard does not certify TLS, external resource identity or artifact provenance.
- [Application defaults](../gym-backend/src/main/resources/application.properties) map `DATABASE_URL`, `DATABASE_USERNAME` and `DATABASE_PASSWORD` into the PostgreSQL datasource. Hibernate validates the schema, SQL initialization defaults to `never`, and Flyway is disabled at runtime with automatic baseline disabled and clean disabled. The separate demo profile enables fixture loading. The existing selector checks are narrower than the proposed production policy, which covers every source that can influence credentials, schema or connections.
- [ReleaseReadiness](../gym-backend/src/main/java/com/fitcore/gym/operations/ReleaseReadiness.java) checks runtime configuration and inspects the live PostgreSQL connection. It checks elevated role flags, schema CREATE, membership in table owners, migration history writes, execution of the catalog-scoping function, required privileges on 29 tables and sequence access. It checks the applied version sequence and success flags. It does not compare migration checksums or certify the full effective ACL and ownership policy. Health and readiness are operational observations.
- [SchemaContract](../gym-backend/src/main/java/com/fitcore/gym/operations/SchemaContract.java) compares the live schema with six reviewed V10 fingerprints for fresh, staged and restored schemas. It covers DDL including columns and defaults, constraints, indexes, relation kinds, triggers and function definitions. Its digest excludes data, ownership, ACLs and Flyway bookkeeping. Two databases can satisfy the same schema contract.
- The clean migration chain is **V1, V2, V4, V5, V6, V7, V8, V9, V10**. V1 captures the baseline without seeds. V2 expands gym ownership. V4 enforces tenant integrity. V5 versions security changes, V6 allows trainer invitations, V7 adds account challenges, V8 adds the transactional outbox, V9 adds catalog lifecycle fields and V10 adds browser session state. V3 is reserved for separately approved legacy mapping. Apply the existing chain to an empty target through the migration identity.

The disposable-only guard, tenant constraints, account checks, default-disabled onboarding and delivery, and existing negative readiness checks remain required for this work. Any production startup implementation needs a separately approved change and its own verification.

## Trust boundaries and bound evidence

| Evidence | Required source and fields |
| --- | --- |
| Target inventory | An authority outside PostgreSQL records the independently approved hosting account or project, resource ID and generation, database name, exact host and port, schema, approved CA digest, runtime and migration role identities, and protected credential references and versions. The credential issuer attests provenance. Secret values stay in the protected resolver. The authority records the approved network route and excludes legacy infrastructure. Reusing a DNS name, database name or credential cannot register a target. Unknown identities fail closed. |
| Workload and artifact | A trusted launcher obtains the platform workload identity and an authenticated, unique boot identity. It verifies the immutable backend artifact digest, its provenance and the digest of the effective deployment configuration. The boot identity includes proof of possession from the launcher. Environment strings claiming an identity or digest cannot establish either. |
| Migration certification | A separate migration job verifies the target and TLS against its own approved operation. Before the initial migration it proves that the new target has no application objects or migration history. It applies the immutable bundle with its migration role. Automatic baseline, repair, clean and fixture SQL are prohibited. Missing, extra, pending or failed history is a rejection. Certification binds the artifact and PostgreSQL version, exact ordered history rows with rank, version, script, type, checksum and success, the bundle’s SHA-256 digest, the approved exact `SchemaContract` digest, and the reviewed privilege policy digest. The expected bundle and checksums come from the reviewed release, with Flyway validation as a separate check. |
| Recovery certification | An independent recovery approver signs the exact resource, generation and recovery epoch, backup artifact and drill evidence digests, test timestamps, approved RPO/RTO outcomes, restore reconciliation, session invalidation and restored-account hold evidence, and an expiry. Evidence lives outside the database and names its scope. The release grant binds this certificate’s digest. |
| Release authorization | A separately trusted release signer issues a purpose-bound, versioned grant containing an authorization ID, target inventory digest, workload and boot identity, artifact and configuration digests, role identities and protected credential references and versions, migration and recovery certificate digests, recovery epoch, and issue, earliest-use and expiry times. The launcher pins trusted signer identities through independent configuration. Neither application operators nor database roles can supply trust roots through the grant. |
| Current authorization state | A trusted, authenticated authority outside backups supplies a fresh, request-bound decision for the boot identity and grant. It confirms the active target generation, current epoch, grant and key revocation, recovery holds and lease deadline. Failure to fetch or authenticate current state blocks admission. The authority must preserve monotonic state across failover and its own recovery. |

Production signers, key custody and rotation, wire envelope and trust roots require approval. Verify the signature over an unambiguous, bounded representation with explicit purpose, version and audience. Reject duplicate, missing or unexpected fields, ambiguous encodings, unknown versions and key IDs, unsupported algorithms, expired or future grants and inconsistent time windows. Do not fetch verifier keys from URLs in a grant. The prototype uses ephemeral, purpose-separated Ed25519 keys in tests. It does not select production key owners or an envelope.

## Admission and recovery

1. **Before any database socket**, the launcher verifies the release artifact, configuration, workload and boot identity. It checks the signed grant, independent recovery certificate and fresh authority decision against the registered target. Deny unknown and legacy targets even if a correctly signed grant names them. Keep the app and workers unstarted while checking.
2. Build a single datasource from the certified tuple. Pin the network route and require authenticated PostgreSQL TLS with `sslmode=verify-full`, the registered hostname and the independently approved CA. Enforce the minimum protocol and credential policy approved for the target. Authenticate the service endpoint and ensure its platform identity maps to the exact registered database resource and generation. Egress and credential issuance must be restricted to that resource. A shared hostname or shared CA alone cannot distinguish a copied database. [pgJDBC TLS documentation](https://jdbc.postgresql.org/documentation/ssl/)
3. Enforce a closed configuration surface before Spring, Hikari, Hibernate or Flyway can create a connection. Check effective values and provenance across inherited environment and relaxed aliases, command-line arguments, JVM properties, profiles, configuration imports and mounted configuration. Reject caller-supplied JDBC URLs and options, alternate drivers or datasource factories, JNDI, Hikari datasource properties or initialization SQL, username or schema overrides, and runtime Flyway selectors or credentials. Resolve only the approved credential reference and version from the protected issuer, and bind its attested provenance to the connection descriptor. Construct the pool from verified inputs only. Verify each new physical connection against the same route, TLS, role and schema policy. Use a dedicated migrator invocation with separate credentials, artifact and authorization. The runtime does not receive those credentials or run migrations.
4. On a bounded preflight connection made as the exact runtime login, confirm database name, effective and session user, selected schema and search path. Use trusted catalog functions and schema-qualified history reads. Verify actual TLS and approved server identity. Require the existing readiness checks plus an approved effective privilege inventory. Include inherited and settable roles, PUBLIC and default grants, object ownership and grant options, temporary schema and database privileges, sequence writes, privileged functions, and access to other databases and schemas. Permit only the runtime DML, sequences and history reads required by the reviewed release. Compare history to the approved certification and check the exact schema digest. Drift, timeout or inability to inspect blocks startup.
5. Recheck live authorization before opening listeners or running workers. Keep the admission decision time-bounded for the running workload. When authorization is revoked or expires, the authority becomes unreachable past its approved freshness limit, or observed target or schema evidence changes, withdraw readiness and stop admitting traffic and jobs. Close the pool and fence access at the ingress and credential boundary. Operators must approve the maximum detection and shutdown bounds and handling of in-flight work.
6. For restore or failover that replaces the database generation, hold admission and advance the recovery epoch outside PostgreSQL before making the restored database reachable. Reattest the new resource and route, rotate credentials, reconcile history, data and privileges, and invalidate restored browser sessions, JWTs, challenges and unsafe queued work under a reviewed recovery procedure. Place all restored identities on an external authentication hold before reactivation. Restored passwords, enabled flags, roles and verified addresses are historical state. Independent recovery must confirm current account control, authorized role, status and address, reset credentials and issue an audited account reactivation receipt for the exact identity and epoch. The hold covers fresh login and ordinary role management cannot release it. Bind this evidence into fresh recovery and release approvals for that generation and epoch. Keep the original endpoint fenced until retirement or a separately approved rollback. A copied comment, cluster control ID, tables, credentials or signed grant cannot substitute for current external registration and epoch. [Existing recovery procedure](phase9d-recovery-and-release-certification.md#restore-without-credential-revival-or-duplicate-email) [PostgreSQL system information documentation](https://www.postgresql.org/docs/18/functions-info.html)

Return a redacted decision code for each rejection and retain an audit record keyed by grant ID, artifact digest, target ID and epoch. Keep credentials, signed envelopes, connection strings, tokens and raw database contents out of logs. A successful health or schema check, a feature flag and a database comment supply no release authorization.

## Local acceptance evidence

[CertifiedStartupContractTest](../gym-backend/src/test/java/com/fitcore/gym/tenancy/CertifiedStartupContractTest.java) models verified inventory, boot identity and current authority state as separate test inputs. Its preflight opens only an owned disposable PostgreSQL endpoint. It uses temporary TLS trust material and a runtime login, runs the existing migrations with a separate fixture migration role, and checks the actual restricted connection. It never starts Spring or changes the runtime guard.

| Case | Expected proof |
| --- | --- |
| Current signed release and recovery approval | One restricted TLS connection passes identity, history, schema and privilege checks after an independent fixture migration. |
| Unknown or synthetic legacy identity, changed hostname, port, database or schema | Rejected before a connection attempt even with valid test signatures and matching reported live state when the independent inventory disagrees. Existing FoundationSafety tests cover Spring, Hikari and Flyway selectors on the current application. |
| Forged, expired, future, revoked or stale release approval, authority unavailable or holding, wrong epoch, workload, boot, artifact or config | Rejected before a connection attempt. A valid signature cannot substitute for current authority state. |
| Recovery signature from wrong signer, expired proof, wrong epoch or evidence digest mismatch | Rejected before a connection attempt. |
| CA substitution or migration credentials at runtime | Rejected by connection policy. A real TLS handshake with an untrusted server certificate and a real wrong-password authentication each fail. |
| Checksum drift, DDL drift, schema CREATE or migration-role membership | Rejected on the restricted live connection. Restoring the fixture’s valid state makes preflight pass again. |
| Actual archive restored into a second owned database | Restored history and restricted schema readiness pass with the source fixture’s CA, certificate and runtime password. The earlier grant fails before dialing because the restored identity differs. A changed generation alone or a changed external epoch alone also blocks the grant. |
| Existing auth, tenancy and business functionality | The complete release script must pass, including its required new contract suite. |

The prototype exercises these decisions on genuine fixture connections. The production adapter still needs tests for the signed wire parser, real platform identity and TLS route attestation, config provenance across all sources, live lease renewal and enforcement, effective ACL inventory, and audited restore fencing. Synthetic recovery metadata supplies no real backup certification. Fixture approvals have no application startup effect.

## Decisions required for implementation

- Name the release signer, independent recovery approver and authority operator. Approve the service that can verify workload and database resource identities, manage external epochs and holds, and authenticate fresh revocation decisions. Approve signer custody, verification trust roots, rotation and emergency revocation.
- Approve the independent target inventory and egress boundaries, TLS CA and certificate lifecycle, allowed PostgreSQL version, exact runtime/migrator/ownership privileges and credential issuance. Authorize access to named resources separately when those resources exist.
- Approve grant, freshness, retry and shutdown deadlines, trusted clock bounds, continuity policy, and how ingress and credential fencing handle existing connections and in-flight work.
- Approve backup evidence scope, RPO/RTO, encrypted archive and key custody, exact restore and failover procedures, evidence signoff and reactivation criteria.
- Approve the immutable artifact and configuration provenance scheme, the release verifier deployment boundary, and independent security review. The release checklist carries the remaining operational approvals.

The next decision is to **name and approve the independent startup trust authority and its operators**. This establishes who can attest the new workload and database resource, issue release and recovery approvals, and revoke them outside PostgreSQL. The decision authorizes design and implementation review within the approved scope. Provisioning and startup require their own approvals.
